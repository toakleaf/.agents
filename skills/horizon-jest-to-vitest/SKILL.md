# Horizon Jest to Vitest

When Tyler invokes this skill, migrate about 250 eligible Horizon Jest unit-test files to Vitest and create a draft PR.

This skill is user-only. Do not invoke it implicitly, pass it to subagents, or tell subagents to load it. The parent agent owns selection, coordination, verification, tracking, and PR creation. Subagents receive only bounded file lists and the migration rules they need.

## Requirements

- Work in the `horizon/` project.
- Migrate unit tests only. Exclude visual tests, snapshots used for visual testing, integration tests, and specialized Jest suites whose runtime is not covered by Horizon's Vitest unit configuration.
- Treat the checked-out repository as the source of truth for merged migrations. Any tracked non-visual `*.vi.test.ts` or `*.vi.test.tsx` file is already migrated, whether or not it appears in the tracking file.
- Use `/private/tmp/horizon-jest-to-vitest-migrated-files.txt` only for live reservations that are not yet visible in the authoritative checkout. At the start of a run, after Tyler confirms the checkout includes all merged migration work, prune reservations whose Vitest path is tracked. Do not prune the current batch from its PR branch. Those reservations remain until the PR is merged and a later run sees them in its authoritative starting checkout.
- Run `node scripts/select-candidates.mjs` from this skill directory to reconcile live reservations and select the next batch. Pass `--count` when the batch should differ from the default 250, use `--reserve-count` to size the replacement pool, and pass `--reserve-selected` once the output path is final. The script screens tracked Horizon Jest unit tests, excludes repository migrations and live reservations, writes disjoint primary and reserve manifests, and atomically records both groups as live reservations. Use `--reserve-manifest <path>` to add or repair exact mappings, and release dropped or unused mappings immediately with `--release-manifest <path>`.
- Give `--output` a worktree- or run-unique path, then immediately preserve immutable primary and reserve copies. The reservation lock does not cover output files, so concurrent runs that reuse a generic scratch filename can overwrite each other's manifests even though their live reservations remain safe.
- Selector manifests contain repository-relative paths. Run every manifest-driven filesystem check from the repository root, or prefix each path with the repository root. Running snapshot, existence, or import checks from the skill directory can silently report false misses.
- Concurrent selector processes can otherwise lose reservations between reading the tracking file and atomically replacing it. The selector serializes every reservation mutation with a PID lock next to the tracking file. Use the selector for reservation mutations and do not bypass that lock.
- Before dispatching work, confirm that the selector recorded every path in the complete, deduplicated manifest as a live reservation. If a mapping is missing, reserve the exact manifest with `--reserve-manifest`. Never edit the tracking file directly. Use the selector for every reservation mutation so its lock and count validation stay in effect.
- Use multiple subagents with disjoint batches. Give each subagent an exact file list and prohibit edits outside that list. Every subagent prompt must say that Horizon provides Vitest globals, prohibit direct imports of those globals, and prohibit Prettier. Keep enough files in reserve to replace tests that prove ineligible.
- Because subagents share one worktree, have them rename files with plain `mv` instead of concurrent `git mv` commands. Git will detect the renames when the parent stages the batch; this avoids `.git/index.lock` contention. Never delete an index lock that another agent may own.
- Do not exclude an eligible unit test merely because it uses Jest APIs, imports Highcharts, or has file snapshots. Migrate snapshots with the update workflow below. If the final diff contains Highcharts imports, commit with `--no-verify` and report the bypass in the PR handoff rather than dropping those tests.
- Build the reserve only after filtering and verify the primary manifest and reserve are disjoint; when classifying a combined run, account for both failed suites and failed tests reported under otherwise-running suites.
- For extension-only batches, treat static filtering as candidate screening, not proof of compatibility. A test can contain no Jest APIs and still fail under Vitest because of module loading, asset resolution, environment behavior, or the strict console setup. Reserve and run an oversized provisional pool, keep only files whose selected-only Vitest result passes, and immediately release failed or unused reservations. Prefer plain `.ts` tests before `.tsx` tests when building high-confidence replacement reserves.
- After selection, reject paths under directories named `integrationTests` even when the filename looks like a unit test. Filename-only screening can otherwise admit a specialized suite whose shared fixtures still require Jest.
- Do not add new console spies or stubs to silence Vitest's strict-console failures. If a migrated test passes only after suppressing a production warning, drop it and use a reserve candidate.
- Before finalizing the manifest, identify selected Highcharts imports so the commit uses `--no-verify`. Do not drop those files or edit `horizon/highcharts-users.txt` for this migration.
- If a selected file is dropped or replaced, update the tracking document immediately. Reserve the replacement with the selector before releasing the dropped manifest; otherwise the next alphabetic selection can immediately pick the failed file again. Once the replacement reservation is confirmed, release the dropped reservation and keep the count accurate.
- Keep each release manifest single-use and limited to mappings this run still owns. Do not include paths this run already released in a later cumulative or broad unused-reserve release: another concurrent run may have reserved those paths in the meantime. If the selector releases more mappings than expected, locate the other run's current active manifest and repair only those reservations with `--reserve-manifest` before continuing.
- Keep a run-unique cumulative reject manifest containing every incompatible candidate. Before assigning any later reserve or replacement batch, subtract that manifest. Released failures become eligible on later selector calls because the tracking file records only live reservations. When another selector call is needed, run it before releasing the current failures when possible. If failures were already released, oversize the new pool, filter it against the cumulative reject manifest, and immediately release every filtered reservation.
- Before any later selector call in a worktree with active renames, re-reserve the exact current active manifest. If a live reservation disappears, the selector can otherwise treat a tracked-but-renamed Jest path as a fresh candidate and fail when it tries to read the absent source file.
- Preserve source-code and test behavior. Do not change production files, test names, assertions, fixtures, values, or control flow. Make only the platform changes needed to run the same tests under Vitest.
- Rename `*.test.ts` and `*.test.tsx` to `*.vi.test.ts` and `*.vi.test.tsx`, then replace Jest APIs and types with their Vitest equivalents.
- Do not change shared configuration merely to accommodate a migrated test. If a test requires a genuinely unsupported environment or behavior, drop it from this batch and use a reserve candidate.
- When Tyler explicitly expands the run beyond the default unit-test scope, audit test entry points as well as the selector output. `scripts/typecheck` and `scripts/oxlint` have a standalone Jest configuration for `*.test.mjs`, and `node/buildScripts/e2eTests` contains Bazel-oriented tests excluded by Horizon's unit Jest config. Rename those files, add `mjs` to the unit Vitest include when needed, and move their package scripts and CI commands to Vitest. Do not treat a clean unit `jest --listTests` result as proof that these specialized nonvisual suites are migrated.

## Migration notes

- Horizon's unit Vitest config sets `globals: true`, and `horizon/typings/test/index.d.ts` loads `vitest/globals`. Do not import global runtime APIs such as `describe`, `it`, `test`, `expect`, lifecycle hooks, or `vi` from `vitest`. Import a Vitest type only when the test actually uses a type that is not globally declared, and use a type-only import.
- Keep each file's existing `owner(...)` declaration on the first line. When adding a type-only Vitest import, place it after the owner declaration; Horizon lint rejects tests with imports before `owner(...)`.
- `vi.mock` factories are hoisted. Values referenced by a factory may need `vi.hoisted`; preserve the original default-versus-named export shape.
- When a `vi.mock` factory defines a local with the same name as a test-file import, give the factory local a distinct name and return it under the expected export key; otherwise Horizon's `no-shadow` rule fails.
- A mock called with `new` must be constructable. Use a regular function or class instead of an arrow-function implementation. Test-only classes may need an explicit `public constructor` to satisfy lint. When `prefer-arrow-callback` rejects a necessary regular-function mock, add a narrow `// eslint-disable-next-line prefer-arrow-callback` comment rather than making the mock non-constructable.
- Remove Jest-only mock options such as `{ virtual: true }` when Vitest does not support them, without changing the mocked module's behavior.
- Horizon's global `mockOptions` is `{ virtual: true }`. Remove the trailing `mockOptions` argument from migrated `vi.mock` calls; passing tests do not reliably expose this leftover.
- Use the existing Vitest environment selected by the surrounding tests. Add a per-file environment annotation only when the old test truly depends on it.
- When a networked test uses `jest-fetch-mock` or needs a relative-URL `Request` shim, prefer `setupMocks`/`server` from `~/ui/mirage/fixtures` with inline routes and Mirage `Response`; Pretender also handles FormData and pending Promise handlers.
- When a renamed test uses file snapshots, run that test with Vitest's snapshot-update flag, such as `pnpm vitest:unit <file> -u`, so Vitest generates the `.vi.test.*.snap` file. Review the generated snapshot, then remove the old Jest snapshot. Do not hand-edit the generated snapshot. Horizon's static analysis fails on obsolete snapshot files even when every assertion passes.
- After updating snapshots for multiple files in one Vitest command, compare the reported test-file count with the snapshot manifest. A filtered file can be absent from the summary while the other files run. Rerun every missing path individually before treating the snapshot batch as covered.
- Reject updated snapshots or inline snapshots that contain an absolute checkout path from an asset import. Assert against the imported asset identity instead, and verify Horizon's Vitest asset stub keeps project asset names relative to the Horizon root.
- Watch for Jest namespace types, `jest.requireActual`, timer APIs, spies, and constructor mocks. Translate them directly; do not rewrite the test around the incompatibility.
- For partial mocks that only spread the actual module, prefer `vi.importActual<object>(...)`. Horizon's `consistent-type-imports` rule rejects `typeof import(...)` annotations; use a regular type-only import instead when the mock needs a specific exported type.
- When an unchanged shared test helper still calls `jest.fn()` and editing that helper would exceed the selected file list, use Horizon's existing scoped bridge: `beforeAll(() => vi.stubGlobal('jest', vi));` with `afterAll(() => vi.unstubAllGlobals());`. Use it only when the helper is otherwise Vitest-compatible and the combined run passes. Translate every Jest API in the migrated test itself instead of hiding it behind this bridge.
- When an unchanged helper calls `jest` during module evaluation, `beforeAll` is too late. Install the bridge with `vi.hoisted`. Do not clean up that hoisted bridge if the combined run shows an `EnvironmentTeardownError` from late lazy imports; cleanup can remove `jest` while another selected file is still loading. Keep the worker-lifetime bridge only when the full selected batch passes and every Jest API in the migrated test itself is translated.
- Testing Library's `waitFor` can time out under Vitest fake timers because its polling timer does not advance. Preserve the existing test body and assertions by using `vi.useFakeTimers({ shouldAdvanceTime: true })` when the old test combines fake timers with `waitFor`.
- Vitest counts every failed `waitFor` polling attempt toward `expect.assertions(n)`, and its matcher error text differs from Jest. If a test waits for a positive call assertion to fail only to prove that the call never happened, replace that Jest-specific control flow with a direct negative call assertion. Do not assert on matcher error-message text.
- A test can pass alone but fail in the combined run when mutable property or module-mock state leaks between files. Set each affected `testProperties` baseline explicitly in `beforeEach`, and prefer an imported auto-mocked function with `vi.mocked(...).mockReturnValue(...)` over a mock factory that closes over mutable file-local state. `mockGetBoundingClientRect(...)` directly replaces `HTMLElement.prototype.getBoundingClientRect`; capture its returned restore function and call it in `afterAll`.
- When a parent unit test only needs to prove that it selects a lazy child and passes visible content through it, mock the immediate component boundary instead of importing the child's lazy implementation. Keep the parent's branch and visible-content assertions, and rely on the child's dedicated tests for its internals. This removes unnecessary transforms and scheduler-dependent failures from the parent test. Do not fix them by extending `waitFor` timeouts.
- A test can finish its assertions while descendants still lazy-load modules, then fail with `EnvironmentTeardownError: Closing rpc while "onUserConsoleLog" was pending` or `Vite module runner has been closed`. Rerun the reported file with related files. If the existing assertion is satisfied before the lazy import becomes observable, wrap `await vi.dynamicImportSettled()` in Testing Library's `act` before teardown; calling it outside `act` can trigger strict-console state-update warnings. If no existing assertion can wait for the lazy output and settling dynamic imports does not resolve the failure, drop the test and use a reserve candidate. Do not add sleeps or silence the logger or console.
- Happy DOM can follow an anchor's synthetic `href="#"` during `userEvent.click` and report an unhandled `localhost` fetch after the assertions pass. Preserve the component click handler while preventing only the test anchor's default navigation.
- Vitest's cross-realm equality does not treat Happy DOM's `Window` as `expect.any(Object)`, and exact plain-object equality can reject a `DOMRect` even when its public fields match. Preserve the assertion by matching the required `DOMRect` fields with `expect.objectContaining(...)` and comparing the window argument to the exact `window` value.
- Horizon's `testHelpers.createStringImportMock` can produce strict React missing-key warnings when a rich string incorporates component arguments. Do not silence the warning or change the assertion. In `vi.hoisted`, temporarily wrap `createStringImportMock` for only the affected string names, add stable keys to object component arguments passed to `incorporateComponents`, and restore the original helper immediately after imports. Follow an existing migrated test that uses `restoreCreateStringImportMock`.
- Format through the repository's root UI formatter, which routes Horizon files to Oxfmt. Run `pnpm format` and `pnpm format:check` from the repository root. Do not invoke Prettier directly.

## Verification and handoff

1. After subagents finish, inspect every diff. Confirm the manifest is disjoint, the count is near 250, no visual tests or production files changed, no stale Jest APIs remain, and migrated files do not import Vitest globals. Account for every non-test file in the diff.
2. Run all migrated files together from `horizon/` with `pnpm vitest:unit <files>`. A collection of individually passing batches is not sufficient. Diagnose failures and rerun the combined set until it passes.
3. Run `pnpm format` and `pnpm format:check` from the repository root, then run the relevant Horizon lint checks for every migrated file. `pnpm lint:diff` can omit untracked rename targets before staging, so stage the final rename set first or run `pnpm oxlint <horizon-relative-paths>` from `horizon/` with the exact migrated paths. Do not run that exact-path command from the repository root; it can bypass Horizon's lint wrapper and miss errors. Do not rely on the commit hook as the only formatting check. If the commit will use `--no-verify`, also run `pnpm exec oxfmt --write <changed-files>` and `pnpm exec oxfmt --check <changed-files>` from the repository root with the exact changed UI files. If the root formatter reports zero matched files while staged UI files exist, verify the active worktree root and run Oxfmt directly.
4. Run `bdev fix --changed`, review the generated BUILD-file changes, then run `bdev fix --changed --check`. A globals-only migration should not add `//horizon:node_modules/vitest` to Bazel `test_deps`. Such additions usually mean a redundant direct import remains. Remove the import and rerun `bdev fix`. Keep a Vitest BUILD dependency only when the test has a necessary direct module import, such as a non-global type-only import.
   If the run is intended to retire nonvisual Jest, also expand the active root Bazel test suites with `bazel query 'tests(//:react_test)'` and `bazel query 'tests(//horizon:horizon_test)'`. Horizon's generated React and `r9build_scripts` packages still expose Jest targets even after all files are named `*.vi.test.*`; remove Horizon's Jest/static aggregates from the active suites while retaining the visual Jest target. The generated dormant targets require a future `rules_r9` Vitest-capable macro before they can be removed entirely.
5. Reconcile `/private/tmp/horizon-jest-to-vitest-migrated-files.txt` with the final diff. Preserve other live reservations, remove dropped or unused reservations from this batch, avoid duplicates, and confirm the count. Keep every final mapping reserved after opening the PR. A later run removes it only after an authoritative starting checkout contains the merged Vitest path. Do not wait until completion to record selected files.
6. If this run exposes a repeatable migration, testing, lint, BUILD, CI, or coordination problem that this skill does not cover, update this `SKILL.md` before finishing. Add a short note with the cause and the step that prevents it. Keep one-off file details out of the skill, and do not delegate this update to a subagent.
7. Invoke the `$draft-pr` skill from `/Users/toakleaf/.agents/skills/draft-pr/SKILL.md` and create a draft PR. Include the actual combined Vitest result, lint result, and `bdev fix --changed --check` result in the PR description.

If the tracking document is missing or remains malformed after repository reconciliation, do not guess which unmerged files another branch reserved. Stop and ask Tyler for the authoritative list.
